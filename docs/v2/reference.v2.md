## 思路一：LangGraph 状态机编排（更强调流程可控与可追溯）

你原方案用 LangChain 做线性调用。如果想让流程更“工程化”，可以引入 LangGraph 把每个步骤拆成独立节点，用状态机管理整个生成过程。有一个开源的 AI Interview Coach 项目就是这么做的：它用 LangGraph 的 StateGraph 编排“提取岗位 → 生成题目 → 追问 → 保存”流程，每个节点职责单一，状态在节点间流转，最终把完整会话状态 dump 成 JSON 和 CSV。

对你复现的适配：Node.js 生态里有 LangGraph.js，你可以把“解析资料→提取知识点→生成题目→向量去重”做成四个节点，每个节点可以独立重试、打日志、人工介入。面试时你可以说：“用状态机而不是线性调用，是因为生成过程中某一步失败（比如某个知识点生成题目时 Zod 校验不通过）时，只需要重跑该节点，而不是整条链路重来。”这比单纯说“我用了 LangChain”更能体现对可靠性的思考。代价是引入 LangGraph 会增加一些学习成本，但如果你简历里写了 LangChain，顺带提 LangGraph 是自然的延伸。

## 思路二：多 Agent 分工 + 评分闭环（更强调题目质量而非数量）

你原方案是“一个 LLM 生成 + Zod 校验”。另一种思路是让多个角色分工：一个 Agent 出概念题，一个 Agent 出场景题，一个 Validator Agent 给题目打分，一个 Judge Agent 决定是否采纳或打回重生成。quiz-gen 这个库就是这个模式：conceptual_generator、practical_generator、validator、refiner、judge 五个角色通过 LangGraph 编排，validator 给题目打分（满分 10 分），低于阈值就打回 refiner 重写。

对你复现的适配：你不需要真的接五个模型。可以用同一个模型（或两个不同温度的模型）扮演不同角色。比如：生成 Agent 温度 0.8 追求多样性，Validator Agent 温度 0 追求严格判断。面试时你可以讲：“单次生成的质量不稳定，用评分-打回机制把‘生成’变成‘生成+筛选’，最终输出给用户的题目通过率更高。”这正好呼应你简历里“200+ 样本备赛耗时降至 4 分钟内”的目标——质量提升意味着人工筛选时间减少。

## 思路三：RAG 检索增强生成（更强调“有据可依”而非“凭空生成”）

你原方案是从用户上传资料中提取知识点再生成。另一种思路是先建题库知识库，生成时检索相似题目作为参考。有研究用 RAG 增强 T5 模型从岗位描述生成面试题，BLEU 和 ROUGE-L 分数显著优于无 RAG 的基线。Smart-HR 项目也是类似架构：Milvus 存题库向量，生成时先检索相关题目，再送 LLM 参考生成。

对你复现的适配：你可以建一个小型“优质面试题库”（手动准备 20～30 道高质量题目），存入 Milvus。生成新题时，先检索最相似的 3 道已有题目作为 few-shot 示例注入 prompt，让 LLM 参考这些题目的风格和深度来生成。这样做的面试话术是：“单纯让 LLM 凭空生成，题目质量波动大。用 RAG 检索相似优质题作为参照，相当于给模型一个‘参考答案’，生成结果更稳定。”而且这和你原方案的“向量去重”共用 Milvus，基础设施复用，不增加额外组件。
