## 🏗️ 全局改造：引入“状态机”思想管理流转

原设计中，服务端是线性执行（解析 -> 规划 -> 生成）。结合 **LangGraph 状态机**思想，在 Node.js 端引入一个轻量的“任务状态”概念（不一定非要上 LangGraph.js，可以用简单的状态枚举 + 步骤记录器实现）。

- 改造点：每次任务生成一个 taskId，记录当前处于哪个节点（PARSING -> PLANNING -> GENERATING -> VALIDATING -> DONE），以及每个节点的耗时和重试次数。

- 带来的收益：如果某个知识点生成失败，前端可以通过 taskId 精准请求重试该节点，而不是重跑整条链路。这完美契合你前端“流式展示过程”和“题卡失败重试”的需求。


## 🎯 模块一改造：引入“评分闭环 + 防幻觉校验”

原设计：规划（Zod校验） -> 针对知识点并行生成 -> 前端编辑。
改造后：规划（防幻觉） -> 并行生成 -> **Validator Agent 评分闭环** -> 前端编辑。

**1. 规划层加固（防幻觉）：**

- 结合 Zod，在规划输出的结构化数据中强制增加 evidence（原文依据）字段。

- 工程化动作：Zod 校验通过后，服务端写一个简单的匹配函数，检查 evidence 字符串是否真的存在于解析出的原文中。如果不存在，说明 LLM 在编造知识点，直接丢弃或打回重规划。这是最轻量且有效的防幻觉手段。

**2. 生成层引入“多 Agent 思想”（Validator）：**

- 原设计生成完就直接给前端了。建议在生成之后、返回前端之前，加一个 Validator 节点。

- 工程化动作：用同一个 LLM（但 temperature: 0，追求严谨），对生成的题目进行打分（1-10 分）。评价维度包括：是否紧扣知识点、参考答案是否准确、是否有歧义。

- 低于阈值（如 6 分）的题目，标记为 needs_retry 或直接触发单题重生成。只有通过评分的题目才在前端展示为“确认可用”状态。这呼应了简历中“人工筛题耗时降低”的亮点。


## 🎯 模块二改造：修正去重时机 + 引入 RAG 思想

原设计：整体规划 -> Prompt 去重（相似直接复用题） -> 异步生成 -> 题目去重入库。
改造后：整体规划（生成蓝图） -> **Prompt 检索注入（RAG few-shot）** -> 异步生成 -> **题目去重（入库闸门）**

**1. 整体规划层重构（生成蓝图而非 Prompt）：**

- 不要让 LLM 直接输出一大段 Prompt 去生成题目。让它输出结构化的“题目蓝图”（包含考察点、题型、难度、对应JD/简历条目）。

- 工程化动作：Node.js 侧用代码模板，将蓝图字段拼装成最终发送给 LLM 的 Prompt。这样 Prompt 结构可控，才能进行下一步的精准检索。

**2. 生成前：用 RAG 替代“直接复用”（修正原设计漏洞）：**

- 原设计的 Bug：Prompt 相似度高，不代表生成的题目就完全适用当前岗位，直接复用风险极大。

- 改造动作：将当前 Prompt 向量化，去 Milvus 检索相似的历史生成题目。不要直接返回老题目，而是把检索到的 1-3 道高质量老题目，作为 **few-shot 示例** 拼接到当前 Prompt 中。这样既避免了重复踩坑，又保证了生成题目与当前上下文的强相关性。这正是 **RAG 思想**的落地。

**1. 生成后：严格的“题目向量去重”（入库闸门）：**

- 题目生成完毕后，对完整题目（题干 + 答案）做向量化，与题库比对。超过阈值则标记为疑似重复，不入库。这才是你简历中“重复拦截率 95%+”的真正逻辑点。

**1. 异步队列升级（状态机思想的落地）：**

- 使用 p-queue 或 BullMQ。关键改造：每道题生成完成并做完 Validator 评分后，**立即持久化状态（写库）**。这样如果服务崩溃，重启后可以根据蓝图状态，只重新生成那些处于 pending 或 failed 的题目，实现**断点续跑**。
